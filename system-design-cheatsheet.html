1. Clarify requirements

TypeQuestions
FunctionalWhat must the system do? Who uses it? What are the core read and write flows?
ScaleUsers, requests per second, peak factor, data size, and growth rate.
QualityLatency targets (p50/p95/p99), availability, durability, consistency, and cost.

2. Design flow

  1. State requirements and assumptions.
  2. Estimate traffic, storage, bandwidth, and peak load.
  3. Sketch the high-level architecture.
  4. Choose the data model and APIs from access patterns.
  5. Add caching, queues, replicas, and partitioning where justified.
  6. Walk through read/write paths, bottlenecks, and failures.
  7. Close with observability, security, deployment, and trade-offs.

3. Horizontal vs. vertical scaling

DimensionHorizontal / scale outVertical / scale up
What changes?Add more machines or service instances.Add CPU, memory, storage, or network capacity to one machine.
StrengthElastic capacity, fault isolation, and high availability through replicas.Simple operations, shared memory, and minimal application changes.
CostOften more efficient at large scale, but requires distributed-system operations.Fast and convenient initially; large instances can become expensive.
ComplexityLoad balancing, statelessness, partitioning, retries, replication, and coordination.Fewer distributed concerns, but a larger failure domain and a hard hardware limit.
Best fitStateless services, variable traffic, large datasets, and strict availability goals.Small/moderate workloads, hard-to-partition databases, or an immediate bottleneck.
Rule of thumb: scale vertically first when the bottleneck is localized and one node is still practical. Scale horizontally when one node cannot meet capacity, availability, elasticity, or fault-isolation requirements. A common production design is hybrid: larger nodes + multiple replicas + partitioning when needed.

When to use vertical scaling

  • The workload is small or moderate and simplicity matters.
  • The application or database is difficult to partition.
  • You need a quick capacity increase with little code change.
  • Shared memory, local transactions, or one data set are valuable.
  • Backups and replicas sufficiently mitigate single-node risk.

When to use horizontal scaling

  • Traffic or data exceeds one machine's practical limit.
  • Demand varies and instances should scale elastically.
  • You need high availability and isolated node failures.
  • The service is stateless or state can be externalized or partitioned.
  • Different functions or workloads need independent scaling.

4. Core building blocks

ComponentUse / watch out for
Load balancerDistribute traffic and run health checks; avoid uneven routing and sticky-session traps.
Stateless serviceEasy replica scaling; externalize sessions and other state.
DatabaseRelational for transactions/joins; NoSQL for predictable, high-scale access patterns.
CacheReduce latency and database load; plan TTL, invalidation, staleness, and stampedes.
Queue/streamAbsorb bursts and decouple work; design for retries, duplicates, ordering, and lag.
Object storage/CDNStore and deliver large immutable blobs near users.

6. Data and consistency

  • Model around access patterns; index frequent filters and sorts.
  • Use transactions for invariants that must change atomically.
  • Use read replicas for read-heavy systems; account for replication lag.
  • Partition with a key that distributes load evenly and appears in queries.
  • Choose strong, eventual, or read-your-writes consistency per flow.
  • Plan retention, archival, backups, restore testing, and deletion.

7. Reliability checklist

  • Set timeouts on every network call.
  • Use bounded retries with exponential backoff and jitter.
  • Make retried writes idempotent.
  • Add rate limits, circuit breakers, and bulkheads.
  • Define RPO and RTO; test failover and restore.
  • Prefer graceful degradation over total failure.

9. Final interview questions

  • What is the expected peak load, and what happens beyond it?
  • What fails first, and how does the system respond?
  • How are loss, duplication, stale reads, and retries handled?
  • How do we deploy and roll back without an outage?
  • Which assumptions should be validated with load tests?
